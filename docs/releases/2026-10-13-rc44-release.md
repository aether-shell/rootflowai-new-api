## 切换决策与配置差异

真实生产起点已证明旧程序可读取新 schema，既有 session/Redis/普通 API Key 可双向使用；无在途异步任务。将原计划的全站维护收窄为分批排空切换。允许短暂新旧进程并存，只用于已验证的旧业务格式；新 PAT 在旧版不可用，版本过渡期间不开展管理令牌迁移。

1. 五个在线 Ingress 的 `/etc/nginx/conf.d/upstream.conf` 保存原文和 SHA。将 master 的 `:30000` 标记 down，admin `:30001` 临时转到 server-2 `:30000`，逐节点 nginx -t + reload。旧 Nginx worker 完成已接收请求。同时将 new-api/new-api-admin 两个 Service 暂时选到 slave，重载三个 portal-auth-forwarder 的 Nginx 以排空其上游 keepalive；不修改 forwarder 配置。
2. 确认旧 master 没有业务连接/在途任务后，基于当前 Deployment 只 patch 镜像、`SHUTDOWN_TIMEOUT_SECONDS=360`、`terminationGracePeriodSeconds=390`。本次旧 Pod 仍先排空，不能依赖新增退出时间保护旧 Pod。
3. master Ready、内部健康及迁移检查通过后，恢复 master 后端并将两台 slave 后端标记 down，admin 恢复原配置。两个 Service 暂时选到 master，并重载 forwarder；确认两台旧 slave 排空后更新 slave Deployment 同三项差异，保持 2 副本。
4. 三个新 Pod 健康后，两个 Service 恢复原 selector，五个 Ingress 恢复原配置，验证 SHA、端口与公网路由。入口重载会关闭空闲连接；已有流等待自然结束，持续未排空则暂缓替换。
5. 隔离环境最终版本观察不少于 20 分钟后才能切换；全量生产恢复后立即、60 秒及至少 20 分钟观察。

不整份应用历史 k8s YAML，不修改生产 DSN、Session/加密密钥、渠道、价格或 Redis 内容；不发布门户；无付费模型请求。
