## Source and artifact validation

The approved self-owned fork is public; the user explicitly confirmed that publication choice. PR #1 first recorded the existing deployed rc.44 baseline. PR #2 then integrated rc.48 and the official Zstd dependency fix. Both code PRs passed their applicable CI checks before merge.

The release was rebuilt from a clean, detached checkout of the published main commit. Source provenance checks passed before and after building and before each deployment phase. Go buildinfo matches the deployed SHA with `vcs.modified=false`. The build used Bun 1.4.4, Go 1.26.10, PGO, `greenteagc`, the committed pinned Debian base and the existing runtime package/license requirements. No runtime credentials or application data were included.

The same archive, manifest and config digests were verified on all three service nodes before changing the application. The final Debian image passed 21 isolated HTTP checks with synthetic PostgreSQL/Redis data and a local mock upstream, including login/refresh/logout, Origin rejection, token lifecycle, ordinary/gzip/zstd requests, SSE, quota consistency and failed-request non-deduction. No vulnerability PoC or paid upstream request was executed.

## Production changes and acceptance

Only the New API master and slave Deployments changed. The master was updated and its migration verified before the slaves rolled one at a time. Replicas remained one master/two slaves; existing secrets, database connections, mounts and graceful shutdown budgets were retained. Host kernels, SSH, firewalls, database roles and other applications were not changed.

Startup probes were added (5-second interval/timeout, 60 failures), minimum readiness was set to 30 seconds, progress deadline to 1200 seconds, and rolling strategy to zero surge/one unavailable. `TASK_TIMEOUT_MINUTES=1440` explicitly preserves the existing 24-hour policy instead of adopting the newer default.

Final production checks confirmed:

- 3/3 target instances Ready/available, matching manifest and application version, with zero restarts since their new containers started and no old terminating instances.
- The three added columns and audit index exist with expected types; the index is valid and ready.
- Standby replay passed a captured post-release primary WAL watermark. A bounded lag gate was used for continuous writes; the final sample had zero pending bytes and approximately 3 ms replay lag.
- No matching panic or initialization error in the bounded current-container log checks.
- Fourteen independent server-vantage public HTTP checks passed: six version/status checks, six expected unauthenticated 401 responses, and two API-domain page redirects.

This was not a zero-interruption claim. The local rollout observer recorded five HTTP 502 responses, twelve connection/request timeouts and one TLS error across its two actual rollout windows. That observer used the local network/proxy path, so these samples are not a global service SLA or proof of the cause of every client error. The later server-vantage checks and final instance checks passed. Long-term traffic, real payment/email/OAuth/MFA and every customer's workload were not exhaustively tested.

## Recovery and scope

Restricted pre-release Deployment/service/Pod metadata, a replica schema dump, and the previous runtime image archive were retained by the operator. Existing database backups and continuous WAL remain the data recovery source. No columns, data, PV/PVC or shared Redis state were deleted or flushed.

The previous image is an availability fallback only: it retains the known Zstd vulnerability. Any security-preserving functional rollback needs the corrected dependency as well; restoring an older application does not imply reverting database schema.

Core-host kernel activation and private management/Tunnel hardening remain separate work. This documentation commit records the completed release and does not change the deployed source or require redeployment.
